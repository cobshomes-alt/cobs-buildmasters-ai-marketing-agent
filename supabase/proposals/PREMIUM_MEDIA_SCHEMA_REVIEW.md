# Multi-asset schema proposal — NOT APPLIED

Milestone1 requires real foreign keys for every source, atomic versioned saves and protection against deleting a source still used by a timeline. Existing cobs_posts.media_id can protect only one source; placing many unprotected IDs in its JSON body would weaken integrity.

The exact candidate SQL is `premium-media-projects.sql`, outside migrations/. It creates two owner-RLS COBS tables, indexes and invoker functions. It adds one deletion-reservation trigger to cobs_media_assets and appends a new reference predicate to ONLY the existing COBS private-bucket DELETE policy. It does not alter P1 helpers, owner assignments, Auth settings, existing posts/campaign records, unrelated policies or migration history. Future timeline saves replace only the selected project's clip rows in one transaction; originals are never deleted by timeline removal. Existing content approval remains separate.

**No production execution is authorised.** First capture current function/grant/policy definitions, COBS row counts, bucket metadata, triggers/dependencies and project identity through read-only inspection. Check new object names are unused and validate the exact existing Storage DELETE predicate and roles against the prior P1 capture. The proposal deliberately aborts on existing project tables or missing expected policy. Its dynamic policy wrapper preserves the existing expression but is not a substitute for human review of that expression and all permissive policies.

Recovery prerequisites: verify a restorable schema/data backup for affected metadata, export the exact original Storage pg_policies row and generate the exact ALTER POLICY rollback from it. Rehearse both directions in isolated Postgres with the current definitions. This current milestone does not claim a fresh production snapshot or exact live rollback capture.

Rollback before any project records exist: transactionally restore the captured original policy expression/roles, drop ONLY cobs_edit_asset_guard trigger, then new clip trigger/table and project table, then newly introduced functions/indexes (indexes drop with tables). Explicitly check both new tables are empty and abort otherwise; never cascade into unrelated objects. After users save projects, dropping these tables would lose timelines: stop, back up those new records and prepare a forward-compatible recovery/export instead. Do not auto-delete them. SQL transaction failures during installation roll back atomically, subject to normal PostgreSQL transaction semantics; this is not a full-project backup guarantee.

No db push/reset/migration repair or historical registration. Existing migration-history discrepancy and P2 remain pending. If later approved, use a separately reviewed new migration version and agreed registration procedure after resolving the baseline; do not opportunistically register older overlapping files. API errors clearly report unavailable schema instead of pretending cloud saving succeeded.
